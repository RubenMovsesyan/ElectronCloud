ElectronCloud

An electron cloud renderer: what an electron “looks like”. Built on GameEngine, which is developed alongside it.

What this is

src/main.cpp opens a fixed 1920×1080 window and draws ElectronCloud’s own renderer through GameEngine’s graphics::Presenter. The renderer is a CUDA ray marcher through an electron cloud. It draws hydrogen’s 1s orbital; the other orbitals aren’t in yet. One world unit is one ångström. 

app::Application<ElectronCloud> app{
    {.width = 1920, .height = 1080, .title = "ElectronCloud", .resizable = false}, argc, argv};
app.run();

The app is a State type (ElectronCloud, below): app::Application<S> builds it once the GPU is up (its constructor is init), calls frame() every frame, and destroys it before the GPU goes down (its destructor is cleanup).

Building

git submodule update --init --recursive
./run           # bootstrap ./build if needed, build, launch (needs the CUDA toolkit)
./run clean     # wipe .build first

build.cpp compiles GameEngine’s sources directly (it does not run the engine’s own build.cpp), generates the engine’s shader header with the engine’s bundled sokol-shdc, and links everything into .build/bin/electron_cloud.

The renderer

renderer::ElectronCloudRenderer lives in src/renderer/, not in GameEngine: it is specific to this project. It satisfies GameEngine’s graphics::Renderer concept, so graphics::Presenter draws it like any engine renderer: 

struct ElectronCloud {
    renderer::ElectronCloudRenderer renderer;
    graphics::Presenter presenter;

    explicit ElectronCloud(app::Context&) {}
    void frame(app::Context&) { presenter.present(renderer); }
};

It is a CUDA ray marcher. The State owns a fly Camera (WASD, Space/Ctrl, ESC toggles mouse-look), the renderer::Atom whose cloud is drawn, and the transition between two orbitals that may be playing: 

renderer::Atom atom{
    .nucleus = Eigen::Vector3f::Zero(),
    .nuclear_charge = 1.0f,     // Z
    .bohr_radius = 0.529f,      // world units per Bohr radius: world units are angstroms
    .bounds_radius = 2.5f,      // density is 0 outside; rays are only marched inside
    .states = {renderer::QuantumState{.n = 1, .l = 0, .m = 0}},
    .state_count = 1,           // 2 = a transition in progress, weighted by .superposition
};

void frame(app::Context& context) {
    ...
    advanceTransition(dt);   // sets atom.superposition for this moment of the transition
    renderer.beginFrame(camera, simulation_time);
    renderer.submit(atom);
    presenter.present(renderer, overlay);
}

The renderer also takes RaymarchSettings (step_size, max_distance, min_density, opacity_cutoff) and a purely cosmetic Appearance (cloud colour, background colour, absorption, brightness). All of these live in raymarch_params.h and are the same types on the CPU and in the CUDA kernel (Eigen included); the kernel receives them by value in one RaymarchParams.

Every frame the raymarch kernel (electron_cloud_renderer.cu) marches one ray per pixel through the part of the atom’s bounds the ray crosses, step_size at a time. At every sample checkRay() returns the cloud’s density, |ψ|². It converts the sample to spherical coordinates around the nucleus, looks up the orbital from the quantum numbers, and switches on it. Only 1s is implemented; anything else is empty space for now: 

__device__ f32 checkRay(const Vector3f& position, const Atom& atom, f64 time) {
    const Spherical point = toSpherical(position - atom.nucleus);
    const f32 a = atom.bohr_radius / atom.nuclear_charge;

    const QuantumState& state = atom.states[0];
    switch (orbitalFor(state.n, state.l, state.m).value_or(Orbital::Count)) {
        case Orbital::S1:
            return density1s(point, a);   // e^(-2r/a) / (pi a^3)
        default:
            return 0.0f;
    }
}

Density is scaled so each orbital peaks at 1, then blended front to back as emission and absorption, kept separate and both linear in density. Each sample gives off light in proportion to its density (brightness scales it, like exposure), dimmed by what the cloud in front has already blocked, and blocks some of the light behind it (absorption, Beer-Lambert). With absorption 0 a pixel is the total probability along its ray; higher absorption lets the front hide the back. Both are sliders in the debug panel. 

const f32 transmittance = 1.0f - accumulated_opacity;
accumulated_color += appearance.cloud_color * (appearance.brightness * density * march.step_size * transmittance);

const f32 alpha = 1.0f - expf(-density * march.step_size * appearance.absorption);
accumulated_opacity += transmittance * alpha;

CUDA can only share buffers with Vulkan in this engine, not images, so the kernel writes RGBA8 pixels into a shared buffer and a fullscreen pass (shaders/electron_cloud.glsl) copies them into the image render() returns. Two timeline semaphores keep CUDA and Vulkan off the buffer at the same time: CUDA waits for the previous frame’s copy to finish before writing, and the copy waits for CUDA. CUDA runs on the render thread, inside render().

Transitions

The debug panel can drive the electron from the current orbital to another with resonant light (a Rabi oscillation). In atomic units, with the light polarised along the transition dipole d and field E0 (from the laser intensity): 

c_A = cos(Ωt/2),   c_B = -i sin(Ωt/2),   Ω = |d| E0,   ω0 = E_B - E_A
|Ψ|² = cos²(Ωt/2) ψ_A² + sin²(Ωt/2) ψ_B² - sin(Ωt) sin(ω0 t) ψ_A ψ_B

The CPU turns that into three weights each frame; the kernel evaluates both wave functions and combines them. The last term makes the cloud slosh at ω0 — the oscillating dipole that absorbs the light — |ω0|/(2Ω) times before the transition ends at t = π/Ω with the electron entirely in B. All of it is physical except the playback speed: 1s → 2p_z at 1012 W/cm² takes 19 fs and sloshes 47 times, shown over however many seconds you choose.

Each orbital has its own colour, spaced evenly round the hue wheel; during a transition the colour turns from the start orbital’s hue to the target’s (the shorter way round) as the population moves, so colour and shape arrive together.

Dipoles are integrated numerically from the same wave functions the renderer draws, so the flags are exact for these orbitals. Forbidden transitions (dipole 0) would never happen with light; they are animated as if the dipole were 1 e a0 and marked in the menu.

Working on GameEngine

external/GameEngine is a full clone of RubenMovsesyan/GameEngine. Engine features ElectronCloud needs are written there, following the engine’s own AGENTS.md (and its docs), committed inside the submodule, pushed to the engine’s remote, then the new submodule pointer is committed here. A new engine source file must be added to both the engine’s build.cpp and the engine_sources list in ours.

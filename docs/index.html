ElectronCloud

An electron cloud renderer: what an electron “looks like”. Built on GameEngine, which is developed alongside it.

What this is

src/main.cpp opens a fixed 1920×1080 window and draws ElectronCloud’s own renderer through GameEngine’s graphics::Presenter. The renderer is a CUDA ray marcher through an electron cloud. Its inputs describe a whole atom, but the wave function isn’t in yet, so it still draws a test sphere. 

app::Application<ElectronCloud> app{
    {.width = 1920, .height = 1080, .title = "ElectronCloud", .resizable = false}, argc, argv};
app.run();

The app is a State type (ElectronCloud, below): app::Application<S> builds it once the GPU is up (its constructor is init), calls frame() every frame, and destroys it before the GPU goes down (its destructor is cleanup).

Building

git submodule update --init --recursive
./run           # bootstrap ./build if needed, build, launch (needs the CUDA toolkit)
./run clean     # wipe .build first

build.cpp compiles GameEngine’s sources directly (it does not run the engine’s own build.cpp), generates the engine’s shader header with the engine’s bundled sokol-shdc, and links everything into .build/bin/electron_cloud.

The renderer

renderer::ElectronCloudRenderer lives in src/renderer/, not in GameEngine: it is specific to this project. It satisfies GameEngine’s graphics::Renderer concept, so graphics::Presenter draws it like any engine renderer: 

struct ElectronCloud {
    renderer::ElectronCloudRenderer renderer;
    graphics::Presenter presenter;

    explicit ElectronCloud(app::Context&) {}
    void frame(app::Context&) { presenter.present(renderer); }
};

It is a CUDA ray marcher. The State owns a fly Camera (WASD, Space/Ctrl, ESC toggles mouse-look), the renderer::Atom whose cloud is drawn, and a simulation clock in atomic units of time: 

renderer::Atom atom{
    .nucleus = Eigen::Vector3f::Zero(),
    .nuclear_charge = 1.0f,     // Z
    .bohr_radius = 0.1f,        // world units per Bohr radius
    .bounds_radius = 1.5f,      // density is 0 outside; rays are only marched inside
    .states = {renderer::QuantumState{.n = 1, .l = 0, .m = 0, .amplitude = 1.0f, .phase = 0.0f}},
    .state_count = 1,           // 2 = a superposition, for transitions between levels
};

void frame(app::Context& context) {
    ...
    simulation_time += dt * kAtomicTimePerSecond;   // atomic units (hbar / E_h) per real second
    renderer.beginFrame(camera, simulation_time);
    renderer.submit(atom);
    presenter.present(renderer, overlay);
}

The renderer also takes RaymarchSettings (step_size, max_distance, min_density, opacity_cutoff) and a purely cosmetic Appearance (cloud colour, background colour, absorption). All of these live in raymarch_params.h and are the same types on the CPU and in the CUDA kernel (Eigen included); the kernel receives them by value in one RaymarchParams.

Every frame the raymarch kernel (electron_cloud_renderer.cu) marches one ray per pixel through the part of the atom’s bounds the ray crosses, step_size at a time. At every sample checkRay() returns the cloud’s density. That is where |ψ(r, t)|² will go; for now it is a hard-coded test sphere, 1 at the centre falling linearly to 0 at radius 1: 

__device__ f32 checkRay(const Vector3f& position, const Atom& atom, f64 time) {
    (void)atom;
    (void)time;
    constexpr f32 kTestRadius = 1.0f;
    return fmaxf(0.0f, 1.0f - position.norm() / kTestRadius);
}

Each sample absorbs light (Beer-Lambert) and is blended front to back, so the cloud reads as a cloud: denser parts are brighter and more opaque, and the ray stops once it reaches opacity_cutoff. 

const f32 alpha = 1.0f - expf(-density * march.step_size * appearance.absorption);

const f32 transmittance = 1.0f - accumulated_opacity;
accumulated_color += appearance.cloud_color * (density * transmittance * alpha);
accumulated_opacity += transmittance * alpha;

CUDA can only share buffers with Vulkan in this engine, not images, so the kernel writes RGBA8 pixels into a shared buffer and a fullscreen pass (shaders/electron_cloud.glsl) copies them into the image render() returns. Two timeline semaphores keep CUDA and Vulkan off the buffer at the same time: CUDA waits for the previous frame’s copy to finish before writing, and the copy waits for CUDA. CUDA runs on the render thread, inside render().

Working on GameEngine

external/GameEngine is a full clone of RubenMovsesyan/GameEngine. Engine features ElectronCloud needs are written there, following the engine’s own AGENTS.md (and its docs), committed inside the submodule, pushed to the engine’s remote, then the new submodule pointer is committed here. A new engine source file must be added to both the engine’s build.cpp and the engine_sources list in ours.
